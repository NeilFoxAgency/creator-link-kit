# CLK120 — percent-encoded query delimiters

## Problem

Campaign operators often run a finished tracked URL through an "encode this URL"
tool, paste it from JSON, or let a spreadsheet formula encode the query string.
The separators become `%26` (`&`) or `%3F` (`?`):

```text
https://shop.example.com/offer?utm_source=youtube%26utm_medium=influencer
```

`urllib.parse.parse_qsl` decodes `%26` inside the first value. GA4 therefore
sees one parameter (`utm_source=youtube&utm_medium=influencer`) and never
receives the later UTM keys. Sessions attribute as direct/none even though the
link looks tagged.

This is a different defect from `CLK117` (HTML entities such as `&amp;`) and
from extra literal `?` characters.

## Behavior

`validate_url` and therefore `clk audit`, `clk build` final checks, batch
audits, and the GitHub Action emit **CLK120** (error) when the raw URL contains:

- `%26utm_source=` / `%26utm_medium=` / `%26utm_campaign=` / `%26utm_term=` /
  `%26utm_content=` / `%26utm_id=`
- or the same keys after `%3F` / `%3f`

Matching is case-insensitive on both the hex digits and the `utm_` key.

Encoded ampersands that are **not** followed by a standard UTM key (for example
`bundle=pro%26lite`) are not flagged.

## Fix

Replace the encoded delimiter with a literal `&` or `?` before publishing.
Do not invent missing pairs automatically.
